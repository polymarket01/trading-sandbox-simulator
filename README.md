# Trading Sandbox Simulator · 沙盒交易所

这是一个用于交易机制学习、策略验证与手动交易训练的现货、永续合约模拟交易所。撮合决定订单如何成交，结算负责更新资金与持仓，风控约束哪些交易可以继续。铺单策略为交易提供流动性，可以独立替换。

## 当前具备的交易能力

- **价格与时间优先**：优先匹配更好的价格，同一价格按进入盘口的先后顺序成交。
- **部分成交与跨档成交**：一笔订单可以逐档成交，也可以只成交一部分；未成交数量按订单要求继续挂单或取消。
- **多种订单要求**：支持限价、市价、立即成交后取消剩余数量，以及只挂单、不立即吃单等方式；现货还支持价格保护。
- **明确的撤改单规则**：支持撤单；撮合层区分减量、增量与改价对排队位置的影响。同价减量保留原优先级，增量或改价重新排队。
- **自成交保护**：识别同账户订单之间的相遇，按规则拦截处理，避免意外自成交。
- **资金与持仓衔接**：现货成交连接资产与费用变化；合约同时衔接保证金、持仓、只减仓和强平等配套约束。

## 订单类型与执行方式

订单类型决定如何报价，有效方式决定未成交数量如何处理。

| 能力 | 现货 | 永续合约 | 行为 |
|---|---|---|---|
| 限价单 `limit` | 支持 | 支持 | 按指定价格或更优价格成交，是否保留余量取决于有效方式 |
| 市价单 `market` | 支持 | 支持 | 消耗可用对手盘，未成交余量不挂入盘口 |
| 保护价市价单 `market_protected` | 支持 | — | 在指定价格保护范围内成交，避免无限跨价吃单 |
| 持续有效 `gtc` | 支持 | 支持 | 限价单未成交部分留在盘口，直到成交或撤销 |
| 立即成交后取消 `ioc` | 支持 | 支持 | 允许部分成交，立即取消未成交数量 |
| 只挂单 `post_only` | 支持 | 支持 | 用于限价单；若会立即吃单则拒绝，避免意外成为 taker |

合约单向普通买卖按成交时净持仓结算：反向成交先减仓，超出部分在保证金足额时反手。只减仓订单不会增加仓位或反手。持仓行 close 按钮先撤关联挂单，再按最新仓位提交一次只减仓市价 IOC；单向撤该币对双边挂单，双向仅撤目标持仓方向，撤单未确认则停止。部分成交不会自动追单。

## 原子改单与排队优先级

撮合层支持直接修改盘口中的订单；现货改单服务在市场锁内完成校验与变更，无需调用方拆成两次撤单、下单请求。

- **同价减量保留位置**：例如挂单剩余 10 减到 6，仍保持原来的排队顺序。
- **同价增量重新排队**：例如剩余 6 增到 10，移到该价格队列尾部。
- **改价重新排队**：移入新价格档位并按新顺序排队；现货普通限价改单若穿过对手盘，会进入成交处理，只挂单改单仍受不吃单约束。
- **批量改单**：可一次提交多笔修改；现货批量改单不支持穿过对手盘，调用方需检查逐笔处理结果。

这里的原子性描述服务端一次改单的受保护处理过程，不表示多次 HTTP 请求、任意批次或跨市场操作都具备整体事务保证。

## 撮合性能设计

- **内存订单簿**：按价格组织盘口，同价使用双向链表维护队列，通过订单 ID 索引定位挂单。
- **同价减量局部更新**：撮合核心定位订单后，仅修改订单余量与档位汇总量，不遍历整个队列；这一路径的簿内更新为 O(1)。改价涉及价格档位维护，跨档成交涉及逐笔匹配，不能统一称为 O(1)。
- **档位汇总与增量结果**：维护每档剩余总量，并返回受影响的买卖档位，便于消费方更新盘口。
- **批量报价处理**：撮合层提供批量改单和报价补丁能力，减少逐笔调度开销，供铺单策略使用。

这些是已实现的数据结构与处理能力，不是吞吐量承诺。当前介绍不提供未经可复现压测的 TPS 或毫秒延迟数字；端到端表现还取决于结算、持久化、行情推送、盘口规模与运行硬件。

## 设计要点

**交易规则独立于策略。** 策略决定挂什么单，撮合决定这些订单如何成交。更换铺单策略不应改变订单的排队和成交规则。

**真实订单成交对应实际可成交数量。** 挂单被成交后会减少，订单可以部分成交；展示价格并不意味着任何金额都能在该价格成交。

**虚拟展示与账户交易分开。** 虚拟成交流只用于演示，不参与撮合、不改变用户资产。用户订单仍经过正常的交易处理。公开 K 线与成交列表使用相同来源，实时更新并保留真实成交高低价，后台保存已结束的 1 分钟聚合；异常退出可能丢失尚未落库分钟的虚拟行情。

**重视异常结果与状态核对。** 对重复请求、超时和状态恢复设置处理机制，不能简单把“没有收到回应”理解成“没有成交”。

这些功能适合学习和测试，不代表已经达到生产交易所级别的性能、长期可靠性或实盘接入验收。

## 极简四档铺单

公开版仅附带极简四档策略：参考公开行情，维护两档买单和两档卖单，让使用者可以观察挂单、吃单和盘口变化。

平台区分内部执行模式与普通账户订单模式。内部模式减少演示账户管理成本；普通账户模式经过资产校验、撮合与结算。用户交易的资金和持仓边界仍需明确。

## 虚拟成交流与真实订单模式

默认采用虚拟成交流，生成演示成交记录，不提交订单、不改变资产。紧盘口也可以生成虚拟展示成交。

可选的真实 IOC 模式使用模拟账户提交订单，经过正常撮合与结算，未成交部分取消。这里的“真实”指沙盒内完整订单流程，不连接外部实盘资金。

## 开始使用

准备 Python 3.12 与 Node.js 22，在项目目录运行：

```sh
python3 run_demo.py
```

首次运行自动安装依赖、构建页面，需要联网。

- 交易页：[本机交易终端](http://127.0.0.1:5174/paper/trade/BTCUSDT)
- 登录：`admin`；默认密码：`12345`
- 模拟资金：现货和合约各 **100,000,000 USDT**
- 首次启动：自动启用 BTC 现货、BTC 永续合约的极简四档铺单与虚拟成交流，并读取公开交易规则对齐精度。
- 行情依赖：Binance 公开行情；上游不可用时策略暂停，不伪造可交易报价。
- 数据：保存在 `demo_runtime/`；后续启动保留已保存的策略参数与开关。
- 停止：按 Ctrl+C。端口冲突可加 `--port 5188`。

默认仅监听本机。公开部署前请设置 `PAPER_EXCHANGE_ADMIN_PASSWORD`，并配置适当的访问保护。
